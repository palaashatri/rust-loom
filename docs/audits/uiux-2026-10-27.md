### MAC-03 feasibility probe — 2026-10-29 (source-level only)

MAC-03 remains OPEN. The proposed native material is AppKit `NSVisualEffectView` with the semantic `Titlebar` material; do not call it “Liquid Glass.” Apple documents that material for window titlebars and describes visual-effect views as background views; toolbars use in-window blending ([Titlebar material](https://developer.apple.com/documentation/appkit/nsvisualeffectview/material-swift.enum/titlebar), [NSVisualEffectView](https://developer.apple.com/documentation/appkit/nsvisualeffectview)).

**Feasibility result — stopped before changing the view hierarchy.** `NSWindow.contentView` is a public setter for the highest view in the window hierarchy, but the current Writer/Winit integration requires that root to remain Winit's own view ([NSWindow.contentView](https://developer.apple.com/documentation/appkit/nswindow/contentview)). Writer's `macos_window_evidence::install` gets the `NSView` from Winit's raw AppKit handle and proceeds only when it pointer-equals `window.contentView()`; `capture_sample` repeats the same identity check. The locked Winit source (0.30.13, `src/platform_impl/macos/window_delegate.rs`) creates `WinitView`, installs it as both `contentView` and the initial first responder, and later has `view()` unsafely cast `window.contentView()` back to `WinitView` under the invariant that it is always that type ([creation/root installation](https://github.com/rust-windowing/winit/blob/v0.30.13/src/platform_impl/macos/window_delegate.rs#L633-L657), [root-view cast](https://github.com/rust-windowing/winit/blob/v0.30.13/src/platform_impl/macos/window_delegate.rs#L803-L807)). Placing `WinitView` under a wrapper with Apple's public `NSView.addSubview` changes its superview and next-responder parent ([NSView.addSubview(_:)](https://developer.apple.com/documentation/appkit/nsview/addsubview%28_%3A%29)). Therefore replacing the root or moving `WinitView` under a wrapper violates Winit's source-level type/responder assumptions. The Writer manifest currently enables `objc2-app-kit` features `NSButton`, `NSView`, and `NSWindow`; no material feature or dependency was added because the probe stops at this invariant. A public titlebar-area attachment does exist: Apple documents `NSTitlebarAccessoryViewController` as managing an accessory in the titlebar–toolbar area, with its view contained in `NSVisualEffectView` for blur and fullscreen size/location handling ([NSTitlebarAccessoryViewController](https://developer.apple.com/documentation/appkit/nstitlebaraccessoryviewcontroller), [NSWindow.addTitlebarAccessoryViewController(_:)](https://developer.apple.com/documentation/appkit/nswindow/addtitlebaraccessoryviewcontroller%28_%3A%29)). This is a separate titlebar accessory surface; it does not automatically put material behind Writer's existing Slint toolbar inside Winit's content view. Treat native titlebar material and the Slint toolbar backdrop as separate claims. No wrapper, effect view, or view-hierarchy mutation was added.

The native host evidence remains blocked: `.work/macos-writer-20261029/evidence.jsonl` records `blocked_host_locked`, zero captured samples, material layer-order/transparency blocked, and input/accessibility/lifecycle checks not run. This source review does not establish compositor output, renderer transparency, pointer or keyboard delivery, accessibility-tree preservation, or resize/fullscreen/active/inactive/close behavior.

**Bounded next plan:**

1. Keep `WinitView` as `NSWindow.contentView`. Before code, determine whether Winit provides a supported public host/overlay hook or whether a titlebar accessory can supply the needed toolbar background without replacing or reparenting that view. If neither can preserve Winit's view and event path, stop this composition design; do not use private superview injection.
2. If a supported slot is found, prototype only a toolbar-confined `NSVisualEffectView` with `Titlebar` material behind the renderer. Keep controls, accessibility, and event delivery on the unchanged Winit view. Use an opaque fallback for macOS Reduce Transparency, macOS Increase Contrast, Loom high contrast, and unavailable material; observe AppKit accessibility-display-option changes ([Reduce Transparency](https://developer.apple.com/documentation/appkit/nsworkspace/accessibilitydisplayshouldreducetransparency), [Increase Contrast](https://developer.apple.com/documentation/appkit/nsworkspace/accessibilitydisplayshouldincreasecontrast)).
3. On an unlocked macOS host, verify native layer/compositor output, pointer and keyboard delivery, accessibility tree, and startup, resize, fullscreen, active/inactive, close-guard, and restore behavior. Record each result; keep MAC-03 OPEN until those checks pass.

No Cargo/build/test or CUA was run for this probe because M6/W-06 verification is pending. The bounded source review adds no application acceptance or live-table change.
