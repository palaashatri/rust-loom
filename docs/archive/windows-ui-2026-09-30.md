## Windows, scroll, and design-system audit (2026-09-30)

Verified on Windows 11 x86-64 with Rust 1.98.1 (MSVC), release builds, a 300,000-cell numeric sheet (1,000 rows x 300 columns). Commits `ea15914` and `6f68938`. This records evidence; it does not accept Sheets or change any gate.

**Windows.** First real Windows run of Sheets. A plain `cargo build` failed: the Slint build script overflowed the 1 MiB default main-thread stack. CI only passed because it links with `/STACK:33554432`. `loom-sheets/.cargo/config.toml` now applies the same flag to local builds and tests. The app then launched and rendered correctly (in-window menu, grid, formula bar, tabs). The whole Sheets workspace passes on Windows (319 app, 114 core, 13 formula, 4 range, 2 cache, 1 performance test) and workspace all-target Clippy with `-D warnings` is clean; the app suite alone is 319 tests; the shared `loom-production` suite passes 69/69. Three Windows-only test/lint problems were fixed: two lock-contention assertions assumed `ErrorKind::WouldBlock` (Windows reports a lock violation; the tests now compare against `fs2::lock_contended_error()`), and two helpers were dead code outside their `cfg`. Not yet verified on Windows: native file dialogs, native menu popups, installer packaging, high-DPI scaling, screen-reader output, and the full cross-crate workspace.

**Scroll performance (the "lag").** Root cause: every scroll event ran the full grid projection. It rescanned every cell for the used range and formula count (about 48 ms per event at 300k cells), replaced fourteen models so Slint destroyed and recreated every cell element, and re-decoded object images. That caps scrolling near 20 fps, and it is independent of platform. `scroll_projection.rs` now reuses the dimensions from the last full projection, updates cell models in place, and moves only object positions when the visible window did not change. Measured: scroll callback 48 ms -> 0.4 ms; frame render about 5 ms. The window also materializes two extra rows and columns so a partly scrolled first cell no longer leaves a blank strip. **Correction to earlier evidence:** the "60 fps million-cell scroll" check in `perf_tests.rs` timed only `project_sheet_grid_with_values`, not the scroll callback or a rendered frame, so it could not see this defect. `frame_bench_tests.rs` (`LOOM_FRAME_BENCH=1`) now drives the real scroll callback and renders the window through the software renderer; on Windows the callback measured p95 1.9 ms and a full-window software render p95 21.7 ms. The `sheets-scroll-budget` CI job runs it with `LOOM_FRAME_BENCH=enforce` on Linux, Windows, and both macOS runners (callback under 16.7 ms, render under 45 ms), so the first macOS numbers will come from CI. macOS performance was not measured (no Mac available); the fix removes platform-independent work, but a macOS run is still required before claiming it.

**Grid UX.** Headers are pinned (they used to scroll away with the data). The grid is edge to edge with single-pixel gridlines (neighbouring borders used to stack into a double line). Numbers right-align under General alignment. Row 1 is no longer auto-shaded and bolded; the starter workbook applies real bold. Sheet tabs sit below the grid as the layout contract requires. Floating objects were positioned 36 px left of their anchor cell and now align to it. While a value is typed, the active cell now shows it (a read-only mirror of the formula-bar buffer; the formula bar remains the editor).

**Visual identity and shared chrome (2026-09-30).** One identity for every Loom app, defined once in the shared foundation: Inter (bundled, SIL OFL 1.1) for text, a neutral Apple-like canvas with white surfaces and hairline borders, and a single system-blue accent (light `#0071E3`, dark `#0968D8` fill with `#4DA3FF` for selection and focus). `theme.slint`, `desktop-ui.toml`, and `tokens/loom.toml` hold identical light and dark palettes again (finding 2 below is fixed; high contrast is unchanged). On Windows and Linux, Sheets, Writer, and Present draw one title row: menu on the left, document title centered, minimize/maximize/close on the right, with edge and corner resize handles. The menu, its keyboard navigation, and the frameless-window behaviour are shared code (`LocalMenu*` and `LoomTitleBar` in `loom-ui`; `local_menu_bindings!` and `window_chrome_bindings!` in `loom-desktop`), so the three apps cannot drift. **Downloadable builds (2026-09-30) — verified in CI.** `.github/workflows/release.yml` builds all eight apps for Linux x86-64, Windows x86-64, macOS arm64, and macOS x86-64, smoke-renders Sheets on each OS, and publishes portable archives (no installer): a rolling `nightly` pre-release on every push to `main`, a versioned release for `v*` tags, and workflow artifacts for manual runs. Run `36754078655` (commit `15cff67`) passed all four build jobs and published `nightly` with four archives and `SHA256SUMS.txt`. Two lessons are recorded so they are not repeated: (1) never pass global `RUSTFLAGS` with `/ENTRY` on Windows, because it also reaches proc-macro DLLs and breaks linking, so each app crate sets `windows_subsystem = "windows"` itself; (2) cargo reads `.cargo/config.toml` from the working directory, not from `--manifest-path`, so the 32 MiB Windows stack setting only applies when each app is built from inside its own workspace directory. The builds are unsigned, so Windows SmartScreen and macOS Gatekeeper warn on first launch. The packaged archives were not downloaded and launched by the agent; the Windows and Linux binaries were built and run locally. Signed MSI/DMG/deb packaging remains in the manual full-matrix workflow.

**Rendering backend.** The shared `loom-ui` crate enables Slint's `renderer-femtovg` (OpenGL, GPU) and `renderer-software`; the winit backend uses the GPU renderer by default and the Windows Sheets binary links OpenGL. The software renderer is the deterministic path for headless screenshots and CI. Slint's GPU path draws UI primitives only: it has no effect, transition, or video pipeline. Keynote-class transitions, Motion, and Video will need `wgpu` render surfaces embedded in Slint windows (RFC-0004 is not yet written), and Slint's Skia renderer is available but not enabled. None of this has been benchmarked.

**Sheets clipboard and formula copy (2026-10-01, Windows).** Reading the code and then trying it live showed that Sheets' Copy, Cut and Paste only used a private in-process buffer: nothing reached the system clipboard, so a user could not paste cells from Excel, a web page or Notepad, or copy cells out. Internal Paste also copied formulas verbatim (`=A1+B1` pasted a row down stayed `=A1+B1`). Both are fixed in a new `clipboard_actions` module (the copy/cut/paste handlers moved out of `actions.rs`, which also shrank from 63.4 KB toward its 65.5 KB ceiling). Copy and Cut write tab-separated text to the real clipboard, with formulas shown as their calculated values and cells containing tabs, quotes or line breaks quoted, and keep the raw cells privately; Paste uses the private copy only while the clipboard still holds exactly what Copy wrote (so formulas survive inside Sheets, and relative references move with the paste while `$` references stay) and otherwise reads whatever tab-separated text another program put there (either line ending, a trailing break, quoted cells); one cell pasted over a selection fills it with each formula copy shifted from the selection's top-left, however the selection was dragged. The clipboard is read through `copypasta` 0.10, already in the dependency tree through Slint's backend and now a direct dependency of `loom-sheets-app` (the lockfile gained that edge); tests use an in-memory stand-in so they never touch a real clipboard. Regressions: `clipboard_tests` (copy writes values with quoting; paste moves formulas and keeps absolute references; external TSV including a quoted comma; text copied elsewhere after a Copy wins; single-cell fill with shifted formulas bottom-to-top; cut then paste; no system clipboard falls back to the private copy; one undo removes a whole paste) and TSV and shifting unit tests. Live on Windows: tab-separated text with a quoted `"Big, red"` pasted into A1:C4, a typed `=B2*C2` calculated 3.75, copying A2:D3 put `Apples<TAB>3<TAB>1.25<TAB>3.75` on the clipboard, and pasting at A6 recreated the block with a working formula. **PDF export correctness (2026-10-01, Windows).** Reading the bytes of a Present-exported PDF showed two defects in the shared `loom-pdf` writer used by Writer and Present. First, text was appended to a UTF-8 `String` and written with `as_bytes()`, so any character from U+0080 up was emitted as two bytes (an `é` would show as `Ã©`) and anything outside Latin-1 became garbage; the font objects also named no `/Encoding`. Second, each page registered only the font of its last text call, so a Writer page holding a bold heading and a regular body drew all of it in one face. Now every page registers four base-14 faces (`F1` to `F4`) with `/Encoding /WinAnsiEncoding`, each text call selects its own face, text is written as one WinAnsi byte per character (including curly quotes, dashes, the euro sign and the ellipsis), and characters the base-14 fonts cannot show become `?`. Regressions: `latin1_and_typographic_text_is_written_as_single_winansi_bytes` and `mixed_styles_on_one_page_keep_their_own_fonts` in `loom-pdf`, and `export_pdf_keeps_headings_bold_and_accents_readable` in Writer core; `loom-pdf` 8, Writer 84+84, Present 35+49+2 pass. Still open: no independent PDF reader was available in this session (no poppler, no PDF library), so the checks read the raw PDF structure and bytes, not a rendered page; CJK and other non-WinAnsi text is not exported at all; Writer now exports inline bold, italic and underline runs (`export_pdf_keeps_inline_bold_italic_and_underline_runs`, placed with Helvetica advance widths from `loom_pdf::text_width_pt`), but not colours, sizes, super/subscript or strikethrough, and the page layout still wraps lines without those metrics; and Present's PDF carries titles and text elements but no images. The titles-only `export_pptx_from_titles` exists in core and tests but is not reachable from the Present GUI, which exports PDF only. This does not make either export production-ready.

**Design-system audit findings (all OPEN; none fixed by the commits above).**
1. *Two competing authorities.* The consolidated prose in this file (COLOR.md, TYPOGRAPHY.md, SPREADSHEET.md, MOTION.md, LAYOUT.md) disagrees with the machine-readable contracts that the constitution says win: accent `#B4552D` and canvas `#FAF9F7` (prose) vs `#C4441A` and `#F4F4F6` (contract); motion 120/200/320/500 ms (prose) vs 120/180/220 ms; grid headers 28/40 px and 28 px rows (prose) vs the 26/36/24 px the code uses. `desktop-ui.toml` has no keys for grid header, row header, or row height, so those are unaudited magic numbers.
2. *(Fixed 2026-09-30; kept for the record.) Runtime drifted from the contract.* In the light theme `theme.slint` differs from `desktop-ui.toml` in five roles: `border` (#d7d7de vs #e2e2e8), `border-strong`, `selection-soft`, `shadow` (#00000030 vs #00000014), and `grid-major`. `tokens/loom.toml` and `desktop-ui.toml` agree on every palette role I compared.
3. *Audits are rotted.* `python3 loom-bootstrap/scripts/audit-ui-foundation.py` fails at HEAD on a check about the worksheet-object layer (it still matches an old `root.kinds[idx]` model; `objects.slint` was not touched by these commits), and all 16 tests in `test_audit_ui_foundation.py` fail. COMPONENTS.md and DESIGN_TOKENS.md point to `audit-product-ui.py`, which no longer exists. A green governance run therefore does not prove the design contract holds.
4. *No font was shipped.* (Fixed for Sheets, Writer, and Present on 2026-09-30 by bundling Inter; the contract and TYPOGRAPHY.md still name Noto Sans and need updating, and the other five apps still use the OS face.) Text used to render in each OS's default face, so metrics differed per platform and Linux-generated baselines could not match Windows or macOS.
5. *Shared UI is over budget and noisy.* `loom-ui/ui/components.slint` (42,781 bytes) and `toolkit.slint` (53,007 bytes) exceed the 32 KiB Slint budget, and every build prints dozens of "Exported component ... doesn't inherit Window" warnings that hide real ones. Warnings are supposed to be failures.
6. *Hard-coded colours in an app.* `contracts/desktop-ui.toml` forbids app-local hard-coded colours, but the Sheets cell fill swatches are literal hex values in `components.slint`.
7. *Code-size ratchet.* `loom-sheets-app/src/main.rs` is 109,445 bytes against a 108,783 ceiling (it was 110,364 before these commits; it needs a real extraction, not a raised limit).
8. *Layout tests depend on the host's fonts.* On Linux (Ubuntu, reproduced in WSL, debug profile) two chart layout tests fail, `long_series_and_unit_metadata_do_not_push_the_data_panel_out_of_the_workspace` and `very_long_series_value_and_unit_have_a_keyboard_reading_path`: at 2.0x text scale in a 900x680 window the chart data panel ends 13.5 px below the workspace. They fail identically at `a9607c9`, before these commits, and pass on Windows, where the fallback font is narrower. This is the Linux `sheets` CI job's red result. It is a real overflow on Linux, and it is the concrete cost of finding 4 (no shipped font).
9. *Toolbar.* Sheets still shows a dense row of text-labelled buttons at wide widths. It is not the icon-first, grouped toolbar the contract describes and it has not been redesigned.
