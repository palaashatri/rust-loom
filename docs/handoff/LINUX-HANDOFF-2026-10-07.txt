1. WHAT THIS IS
---------------

decision to the supervising agent (gate standards are in the AGENTS.md

Commit and push after EVERY verified milestone (owner instruction).

2. ROLES FOR THE LINUX SETUP
----------------------------
Orchestrator  = Claude Code, Sonnet 5.5 (low effort). Owns the plan, task
                cards, git, the ledger, CI watching and every commit/push.
                Never writes large code itself; delegates.
Hostile review = Claude Code, Opus 5.5 (high effort). Read-only by default.
                Reviews each coder deliverable BEFORE the orchestrator commits;
                drives the real app windows on Linux; tries to break claims.
                Decides gate PASS/FAIL on evidence. Writes findings, not code
                (it may write tiny repro tests).
Coder         = GPT 6.1 "Sol" through the ChatGPT Codex app. Implements one
                bounded task card at a time. Codex reads AGENTS.md
                automatically; AGENTS.md is large (~140 KB), so give Codex the
                TASK CARD (section 9) and tell it which AGENTS.md paragraphs to
                read, not "read everything". Codex does NOT commit.

Loop per milestone:
  1. Orchestrator writes a task card (template in section 9).
  2. Coder implements in the working tree, runs the gates, reports.
  3. Reviewer verifies independently (re-runs the gates, reads the diff,
     drives the app, mutation-checks new tests: a test that cannot fail is
     not evidence) and answers PASS or a numbered defect list.
  4. Orchestrator commits + pushes only after PASS, updates the ledger in the
     same commit, then watches CI (section 6).
Only ONE coder works on a given app at a time (shared files like main.rs and
app.slint collide). Different apps may run in parallel. Disk and build-lock
contention are real (section 8).

Rules every worker must follow (copied from AGENTS.md "Owner override
2026-10-02", still in force):
  - Work only in the files the card names plus new modules needed to stay
    under size limits. NEVER raise a byte ceiling
    (loom-bootstrap/contracts/code-quality.toml); extract a module instead.
  - Never edit AGENTS.md or READMEs (the orchestrator does). List needed
    README text changes in the report.
  - No git checkout/stash/reset/clean, no cargo clean.
  - Debug builds only for tests (CARGO_INCREMENTAL=0). Use
    CARGO_PROFILE_TEST_OPT_LEVEL=3 for timing benches. A DEBUG build is
    10-30x slower and meaningless for performance claims.
  - Regression test first (see it FAIL), implement, see it pass. Test
    behaviour, not source strings. No placebo controls, no success messages
    without the real effect, no weakened or deleted tests.
  - Finish with: cargo fmt --all; cargo clippy --workspace --all-targets
    -- -D warnings; cargo test --workspace (in each app touched); then from
    the repo root the four audits (section 4). Warnings are failures.

3. LINUX ENVIRONMENT SETUP
--------------------------
  - Rust stable (rustup). Build dependencies are listed in
    .github/workflows/ci.yml (the Linux jobs install them: fontconfig,
    xkbcommon, X11/Wayland libs, etc.). Copy that apt list.
  - python3 (audits use python3 on Linux), zenity (file dialogs fall back to
    zenity when no xdg portal), xdotool + an X11 session for driving windows
    (Wayland blocks synthetic input; use X11/Xwayland or XTEST, NOT
    `xdotool --window` events, which apps did not receive reliably),
    at-spi2 + Orca for accessibility checks, LibreOffice
    (libreoffice-core/calc/writer/impress) for interop checks.
  - GPU window: the winit backend uses Slint femtovg (OpenGL). Headless
    screenshots use the software renderer: `loom-<app> --screenshot out.png
    --size 1280x800 --theme light|dark|high-contrast [--text-scale 1.0-2.0]
    [--scale-factor 1.0-4.0] [--rtl] [--sample (Writer)]`.
  - The Windows-only 32 MiB stack link flag lives in each app's
    .cargo/config.toml; irrelevant on Linux but do not delete it.
  - Isolated state for QA runs: set HOME, XDG_DATA_HOME, XDG_CONFIG_HOME,
    XDG_STATE_HOME to a temp dir, and LOOM_CONFIG_DIR for settings. Without
    that, a recovered draft from a previous run contaminates the next run.
  - CI helper: `gh` may exist on Linux; on the Windows box it did not, so the
    GitHub REST API was used (api.github.com/repos/palaashatri/rust-loom/
    actions/runs). Nightly builds publish to the `nightly` release.

8. PITFALLS LEARNED (save yourself the pain)
--------------------------------------------
  - DISK: the three app target/ folders reach 12-15 GB each. Build one app at
    a time and delete another app's target/ when space is low. The Windows
    drive hit 3 GB free twice. Never run three full workspace builds at once.
  - A DEBUG Writer build takes ~10 s per keystroke on a 300-paragraph paste;
    do not judge speed or hang from debug builds.
  - Headless windows report width 0 until laid out: absolute x positions that
    depend on parent.width went negative and pushed dialog buttons off-screen
    (fixed with max(0px, ...)). Watch for this class of bug in new dialogs.
  - cargo test does NOT rebuild target/debug/loom-<app> (the app binary);
    run cargo build -p loom-<app>-app before using --screenshot.
  - In the qa driver, `--screenshot` captures of full-screen windows return
    the monitor size; do not resize them non-uniformly.
  - Slint Windows glyph/stack: a full-screen slideshow capture is the whole
    monitor.
  - Git emits LF->CRLF warnings on the Windows checkout; harmless. On Linux
    keep LF. The code-structure audit measures LF-normalised bytes.
  - Sonnet-class subagents occasionally hit usage limits mid-edit; always
    re-read git status/diff before resuming a worker, and resume with an
    explicit "you were cut off, here is what is in the tree" message.
  - Do not trust a worker's "tests pass" for large suites: re-run the gate
    yourself or wait for CI, and mutation-check new tests.
  - AGENTS.md size: keep it under ~150 KB; subagents inherit it. Move full
    card text to docs/archive/AGENTS-ARCHIVE.md (authorized).

9. TASK CARD TEMPLATE (give this to the coder)
----------------------------------------------
  TITLE:
  APP(S) AND FILES YOU MAY TOUCH:
  READ FIRST (AGENTS.md paragraphs by heading, not the whole file):
  GOAL (what the user does, what is wrong now, what must happen):
  ACCEPTANCE CHECKS (each must have a test you saw fail first):
  CONSTRAINTS: no byte-ceiling increase, no AGENTS.md/README edits, no
    git history changes, debug builds only, disk budget, do not commit.
  DONE WHEN: fmt, clippy -D warnings, cargo test --workspace in the app,
    the four audits, plus the app run live and a screenshot described.
  REPORT: exact commands, pass counts, changed files, README text changes
    needed, anything not done, anything that needs a screen reader.

REVIEWER CHECKLIST (Opus): re-run the gates; read the diff for weakened
tests, new allow()s, raised ceilings, dead code; mutation-check each new
test by breaking the code under test; drive the real app (keyboard only,
then mouse); check RTL and 2.0x scale; look for placebo controls and success
messages without effect; confirm README claims match behaviour; then answer
PASS or a numbered defect list with severity (1 data loss/crash/corrupt
export, 2 broken primary workflow, 3 polish).
