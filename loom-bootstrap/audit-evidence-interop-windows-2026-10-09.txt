MISMATCH LIST
  1. [severity 3, fixture/test defect, not an app defect] check_excel "CSV opened plainly in Excel keeps accents" FAIL.
     Cause: the fixture (loom-sheets-core/tests/interop_fixtures.rs, line ~195) writes sheets-N.csv from
     to_csv_with_values(...).as_bytes() with no BOM, so Excel reads it as the ANSI code page. The app does not export
     that way: loom-sheets-app/src/workbook_io.rs csv_file_bytes() prepends the UTF-8 BOM (EF BB BF) to every CSV export
     (comment there: Excel reads CSV as the system code page without it). Verified directly: the same fixture CSV with a
     BOM prepended, opened plainly in hidden Excel, returned A4 = "Cafe-acute Zo-diaeresis" correctly (checked by code
     page bytes 0x82/0x89 in OEM output).
     So the real export is NOT affected; the check tests the wrong bytes.
  2. [severity 3, coverage gap] The CSV checks also differ from the app in content: the app exports with
     to_csv_with_formulas (formulas preserved), the fixture uses to_csv_with_values, so "CSV holds calculated values /
     has no formulas" validates a variant the app does not write. The BOM-bearing real export path is untested by Excel.
  3. [not a mismatch, caveat] Windows only. Linux LibreOffice checks were run separately (2026-10-07). Word/PowerPoint
     opened the fixtures; PDFs from Loom were not opened by a PDF viewer here.

RECOMMENDATION (fixture change, do not weaken the check)
  Make the fixture write the same bytes as the app: either move the BOM prefix into a shared loom-sheets-core helper that
  both csv_file_bytes() and interop_fixtures.rs call, or at minimum have the fixture prepend [0xEF,0xBB,0xBF] to
  sheets-1.csv. Preferably also write a second fixture from to_csv_with_formulas through that helper and assert the
  formulas survive. After the change the plain-open check should PASS while "CSV imported as UTF-8" (OpenText, 65001)
  stays unchanged. Tests to add: a core-level test that the shared export helper starts with EF BB BF.
